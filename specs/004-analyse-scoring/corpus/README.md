# Extraction corpus: what is needed from a human (T035a)

**Status: needs-human.** The corpus in `packages/core/test/fixtures/bids/` is **synthesised**. GeM BidPlus is not reachable from the build environment and no genuine GeM PDF was available, so `real-goods-bid.pdf`, `real-service-bid.pdf` and `real-ra-bid.pdf` are generated by `generate-real.ts` in GeM's layout (Hindi-first bilingual labels, wrapped labels, interleaved values, consignee table, header/footer with "Page n of N"). Their `*.expected.json` files are the ground truth printed into each PDF, not extractor output. Nothing in this repo claims these are genuine documents.

SC-001 ("≥ 95 % of labelled fields extracted with the correct value and page by rules alone, on ≥ 3 real-layout bilingual GeM PDFs") is therefore met on synthetic stand-ins only. T035a stays open until genuine, anonymised GeM PDFs are added.

## What SC-001 measures

`packages/core/test/analyse/corpus.test.ts` extracts every PDF with `extractPages` + `extractRequirementsRules` and compares each field listed in its `real-*.expected.json` on **key, value (and numeric where given) and page**. A field counts only when all of these match. The test requires ≥ 95 % per document **and** overall. It also fails on single-valued keys the extractor returns that the JSON does not list (except `bid_published_at`, `consignee_state`), and checks that every requirement has file, page, method `RULE` and a Devanagari-free quote of ≤ 220 characters.

## Who consumes the files

- `packages/core/test/analyse/corpus.test.ts` reads every `real-*.expected.json` in `packages/core/test/fixtures/bids/` and the PDF it names (`file`). Adding a pair is enough; no code change is needed.
- Its structural test currently requires, across the set, one bid with `contract_period=2 years`, one with `bid_to_ra=true` and one with `layout: "interleaved"`, and Devanagari text on page 1 of each. Keep the three synthetic bids until genuine ones cover those cases, or relax the test deliberately in the same PR.
- `e2e/004-analyse/support.ts` and `pdf-text.test.ts` use the other fixtures in that folder (`go-it-services.pdf` etc.), not the `real-*` files.

## How to add a real PDF

1. Download a public bid document from GeM (BidPlus) by hand. Choose varied layouts: goods with OEM criteria, a service bid with a contract period, a reverse-auction bid, a corrigendum, and at least one document that has both Hindi and English labels.
2. **Anonymise** before it enters the repo: replace buyer organisation, officer names, phone numbers, e-mail addresses, consignee addresses and any signature or seal; change the bid number to an invented `GEM/2026/B/<7 digits>` (keep the format). Edit the text layer (not just a black box over it), keep the layout, page count and page numbering, and check with `pdftotext` that no original identifying text remains. Public tender numbers, amounts and dates may stay, but do not keep anything that identifies a person.
3. Name the files `real-<short-name>.pdf` and `real-<short-name>.expected.json` in `packages/core/test/fixtures/bids/`.
4. Write the expected JSON **by reading the PDF** (never by pasting extractor output): `{file, bidNumber, description, layout: "cell"|"interleaved", fields: [{key, value, numeric?, page}]}`. Copy the field list from `real-goods-bid.expected.json`. List every labelled field printed in the document and the page it is on.
5. Run `pnpm --filter @tp/core exec vitest run test/analyse/corpus.test.ts`. A miss below 95 % is an extractor bug to fix in `packages/core/src/analyse/rules.ts` (with a unit test), not a reason to edit the expected JSON.
6. Record the result (documents, fields, accuracy) in the PR and tick T035a.

Licence/consent: only use documents GeM publishes openly, and note in the PR that no personal data remains.
