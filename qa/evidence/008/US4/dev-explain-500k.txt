--   page  ?state=Maharashtra → Index Scan using tenders_open_created_idx, Filter state/coalesce, 201 rows removed
--   count / ministry / category facet → BitmapAnd(tenders_open_closing_idx [30,000], tenders_state_idx [59,404,
--     NON-partial]) → 18–34 ms each. tenders_open_state_idx was never chosen.
--   Why: the planner estimates "still open" (coalesce(end_at,'infinity') >= $now) at the default 1/3 — PostgreSQL
--   ignores expression statistics of PARTIAL indexes (selfuncs.c examine_variable) — so it believed a BitmapAnd with
--   the closing index cut the heap visits 3×, and that walking tenders_open_created_idx was cheaper than a sort.
--
-- FIX: migration 0015 rebuilds tenders_open_state_idx as
--   CREATE INDEX tenders_open_state_idx ON public.tenders USING btree (state, created_at DESC, COALESCE(end_at, 'infinity'::timestamp with time zone)) WHERE (status = 'open'::text)
--   so `state = $1` AND the "still open" expression are both Index Conds and the rows come out in the default sort
--   order (no sort, LIMIT stops after 26 entries); count/facets become one Bitmap Index Scan with both conditions.
--   The feed also writes `status = 'open'` as a literal (the partial indexes' exact predicate, provable under a
--   generic plan), and the total + facets without their own filter now share ONE GROUPING SETS query (finding 2).
